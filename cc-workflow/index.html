The mindset shift

Claude Code is the workbench, not autocomplete.

The biggest change isn't the tool — it's the habit. We don't ask a chatbot for snippets and paste them in. We do the work through Claude Code (CC), running a repeatable protocol that produces evidence at every step.

Improvising
  • Type code by hand; ask a chatbot for help on the side
  • Paste snippets, tweak until it looks right, hope it holds
  • Tests written later — or never
  • "It works on my machine" with no shared evidence
  • Knowledge lives in one person's head
By protocol
  • Agree the spec, then a written plan, before any code
  • Write the failing test first; CC implements until it passes
  • CC writes & runs unit, integration and end-to-end tests
  • "Done" means command output proves it — not a claim
  • Specs, plans and decisions are captured as we go
The non-negotiables

How we test

The machine writes the tests — and runs them

This is the part teams underestimate. Roughly 99% of our tests are authored and executed by Claude Code itself, across three tiers. A human does a final real-device sanity check; CC does everything up to it.

Unitfast · every change

Pure logic in isolation — models, parsers, business rules. Milliseconds to run, so they run constantly. These are written first, before the code they test.

flutter testvitest / jest
Integrationcomponents wired

Several units working together, with fakes standing in for the backend (e.g. mocktail). Proves the pieces talk to each other correctly — no live services needed.

mocktail fakeswidget tests
End-to-endthe real app

The whole app driven like a user. CC launches it, drives it, and reads the result back automatically:

Playwright — web integration_test + adb.exe — Flutter

On the app, e2e runs on the Android emulator and is driven by widget finders, not blind screen taps — so it's reliable, not flaky.

of tests are machine-written and machine-run. Because the failing test comes first, every passing build carries its own proof. CC reports the actual output — pass counts, failures, traces — and we don't call anything "done" without it. e.g. the Casualty AlgoV2 native renderer landed with 73 tests written before the UI existed, verified offline on emulator emulator-5554.
The toolbox

Skills — CC reaches for them automatically

"Skills" are reusable playbooks CC follows step-by-step. You don't call them by name — they're installed once, and CC picks the right one up from how you describe the task. Say "brainstorm this" or "design a screen" and the matching skill kicks in. Process skills decide how to approach the work; build skills guide the doing. Tap a card to expand.

Put it together

Three playbooks for the work you actually do

The principles and skills combine into a handful of repeatable routines. Pick the one that matches your task.

  1. Brainstorm the change into an agreed spec. brainstorming
  2. Write a plan — ordered, testable steps. writing-plans
  3. Isolate the work in a worktree / feature branch. using-git-worktrees
  4. TDD each slice: failing test → implement → green → refactor. test-driven-development
  5. CC runs unit, integration and e2e tests and reports output.
  6. Verify with real evidence before claiming done. verification-before-completion
  7. Review, then open a small PR for human approval. /code-review

On Casualty: the AlgoV2 native renderer went spec → plan → 73 tests first → green → on-device check, shipped on a single feat/algov2 line.

  1. Reproduce & find root cause — don't guess, confirm. systematic-debugging
  2. Write a failing test that captures the bug exactly.
  3. Fix until that test (and all others) go green. test-driven-development
  4. Check for regressions — the whole suite, not just the new test.
  5. Verify the fix with output, then a small, single-purpose PR. verification-before-completion

Why the test first: it turns "I think I fixed it" into a permanent guard that the bug can never silently return.

  1. Brainstorm the intent — who's it for, what's the one job. brainstorming
  2. Set visual direction — palette, type, signature element. frontend-design
  3. Build, screenshot, and self-critique against the brief.
  4. Drive it end-to-end with Playwright (web) or on the emulator (app).
  5. Review and PR like any other change.

Review & merge discipline

Nothing self-merges

Speed comes from the loop, not from skipping the gate. The review discipline is what makes the velocity safe — and it's the heart of the SDLC work landing across the Casualty repos.

→

Small, single-purpose PRs

One change per branch (e.g. feat/algov2). Easy to read, easy to revert.

→

Templates & CODEOWNERS

Issue and PR templates standardise the ask; CODEOWNERS routes each review to the right person.

→

A review pass first

/code-review on the diff before humans look — and ultra for deeper, multi-agent review.

→

CI runs the tests

The suite runs on the PR, not just locally. Adding CI + tests is the top SDLC fix in flight.

→

Human approval gate

Branch protection means a person approves before merge. The machine proposes; people decide.

→

Feedback handled with rigour

Review comments are verified technically, not agreed to reflexively. skill: receiving-code-review

Getting started · for David, Badru & Charles

Set it up, then try it on one real thing

You don't have to adopt the whole protocol on day one. Get CC running, then run a single playbook end-to-end. The habit grows from there.

  1. Install Claude Code.The CLI in your terminal, plus the desktop and IDE (VS Code / JetBrains) integrations. Point it at the repo you're working in.
  2. Add the skills (superpowers + plugins).Install the skill packs shown above so brainstorming, writing-plans, test-driven-development and the rest are available for CC to pick up automatically.
  3. Connect MCP servers as needed.e.g. a browser server for Playwright-driven e2e and visual checks. Add only what a task needs.
  4. Turn auto mode on — behind a guardrail.Let CC run autonomously (auto-accept) so it can read, edit, test and iterate without a prompt on every step. Keep one hard rule: a hook blocks CC from pushing or mutating GitHub, so every push and PR stays a manual, human action. See the appendix for the exact hook.
  5. Write a CLAUDE.md for the repo.Project rules, conventions and "how we do PRs here". CC reads it every session, so the protocol travels with the code.
  6. Run one real playbook.Pick a small, annoying bug. Run Fix a bug end-to-end: root-cause it, write the failing test, fix to green, verify, PR. Feel the loop once.
A note for the SRE in the room

CC proposes; it doesn't get to merge or deploy on its own. Permissions, hooks and branch protection keep destructive and outward-facing actions behind explicit human approval — the same gates you'd want for any teammate with commit access.

Adoption path

Crawl, walk, run

You can climb this ladder one rung at a time. Each rung is useful on its own.

Crawl

Understand & fix

Use CC to explain unfamiliar code and fix one small bug — with a failing test that locks the fix in. Low risk, immediate payoff.

Walk

Build a slice

Take one small feature through the full loop: spec → plan → TDD → verify → PR. Experience the protocol on real work.

Run

Every change, by protocol

All work runs through the loop. CC writes the tests; reviews gate merges; docs and memory accumulate. Velocity with evidence.

Appendix · the guardrail hook

Auto mode, with the brakes wired in

Auto mode lets CC work without a prompt on every step — but a PreToolUse hook intercepts every shell command first and blocks any push or change to GitHub. CC can read, branch, edit, and test freely; pushing and PRs stay manual and human. This is the exact configuration we run.

What it does

The hook runs before every Bash command. It inspects the command and denies it when it's confident the command would mutate a protected GitHub repo — otherwise it stays out of the way. The result: autonomy for the safe 99%, a hard stop on the actions that leave your machine.

Commands it stops

  • git push (and push --delete) to a protected remote
  • git remote set-url pointing at a protected repo
  • mutating gh calls — pr/issue/release create·edit·merge·close, write gh api (POST/PUT/PATCH/DELETE)

Read operations, and work on your own repos, pass through untouched. The GitHub server's own permissions are the backstop if anything slips past.

~/.claude/settings.jsonwires the hook in
"hooks": {
  "PreToolUse": [{
    "matcher": "Bash",
    "hooks": [{
      "type": "command",
      "command":
        "node ~/.claude/hooks/emk-repo-guard.js"
    }]
  }]
}
emk-repo-guard.js — the decisiondeny → manual
// before every Bash command:
if (mutatesProtectedRepo(cmd)) {
  return {
    permissionDecision: "deny",
    reason: "push/PR must be manual —
             AL approves it by hand"
  };
}
// everything else: pass through

Full source: ~/.claude/hooks/emk-repo-guard.js. Scope it to whichever repos or org you want protected.
